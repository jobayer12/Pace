# Backend

NestJS 11 + PostgreSQL + Knex.

## Requirements

- Node.js >= 20 (tested on 22.22.2 — NestJS 11 does not support Node 16)
- PostgreSQL

## Setup

```bash
npm install
cp .env.example .env   # then fill in DB_PASSWORD
createdb load_testing  # or: CREATE DATABASE load_testing;
npm run migrate:latest
npm run start:dev
```

Server listens on `http://localhost:3000/api`.

| URL | What |
| --- | ---- |
| `http://localhost:3000/api` | API |
| `http://localhost:3000/docs` | Swagger UI |
| `http://localhost:3000/docs/json` | OpenAPI spec (JSON) |
| `http://localhost:3000/docs/yaml` | OpenAPI spec (YAML) |
| `http://localhost:3000/metrics` | Prometheus scrape endpoint |

## Schema — `users`

| Column       | Type           | Constraints                          |
| ------------ | -------------- | ------------------------------------ |
| `id`         | `bigserial`    | primary key                          |
| `email`      | `varchar(255)` | not null, unique (btree index)       |
| `first_name` | `varchar(255)` | not null                             |
| `last_name`  | `varchar(255)` | not null                             |
| `created_at` | `timestamptz`  | not null, default `CURRENT_TIMESTAMP` (UTC) |

## API

Interactive docs are at **`/docs`**, generated by `@nestjs/swagger` from the
controller decorators and the `class-validator` rules on the DTOs — so the
documented constraints and the enforced ones cannot drift apart. The raw
OpenAPI 3 spec is at `/docs/json` (or `/docs/yaml`), which is what you would
feed to a client generator or import into Postman/Insomnia.

`User` and the request DTOs carry the schema metadata directly rather than
having parallel "response DTO" classes, so there is still exactly one definition
of the shape.

Set `SWAGGER_ENABLED=false` to turn the docs off. They are **unauthenticated**,
like `/metrics`; neither should be publicly reachable in a deployed environment.

### `POST /api/users`

```json
{ "email": "alice@example.com", "firstName": "Alice", "lastName": "Anderson" }
```

`201` with the created user. Email is trimmed and lowercased. `409` if the email
already exists, `400` on validation failure or unknown properties.

### `GET /api/users/:id`

`200` with the user, `404` if absent, `400` if `id` is not a positive integer.

### `GET /api/users/email/:email`

`200` with the user, `404` if absent. Lookup is case-insensitive (the value is
lowercased before querying, matching how emails are stored).

### `GET /api/users?page=1&limit=20`

`limit` defaults to `20` and is capped at `100`; `page` defaults to `1`. Values
outside those bounds return `400`.

```json
{
  "data": [{ "id": "1", "email": "...", "firstName": "...", "lastName": "...", "createdAt": "2026-09-21T17:04:39.859Z" }],
  "meta": { "page": 1, "limit": 20, "total": 25, "totalPages": 2, "hasNextPage": true, "hasPreviousPage": false }
}
```

## Observability

### Logging (Winston)

Winston replaces Nest's built-in logger via `nest-winston`, so framework
bootstrap output and application logs share one transport and format.
`bufferLogs: true` holds the earliest startup lines until Winston is ready.

- **Development** — colourised, human-readable Nest-style output.
- **Production** (`NODE_ENV=production`) — one JSON object per line, with a
  `service` field, ready for a log shipper.

Every request gets an `x-request-id` (inbound header honoured, otherwise a UUID),
echoed back on the response and attached to its access log line. Access logs are
emitted at a level derived from the status: `error` for 5xx, `warn` for 4xx,
`info` otherwise.

```json
{"level":"info","message":"GET /api/users 200","context":"HTTP","requestId":"f0aa50d8-…",
 "method":"GET","url":"/api/users","route":"/api/users","statusCode":200,
 "durationMs":11.315,"ip":"::1","userAgent":"curl/8.7.1","contentLength":648,
 "service":"backend","timestamp":"2026-09-21T17:25:51.512Z"}
```

### Metrics (Prometheus)

Exposed at **`GET /metrics`**, outside the `/api` prefix where scrapers expect it.
Built on [`@prometheus-io/client`](https://www.npmjs.com/package/@prometheus-io/client)
(the maintained successor to the now-deprecated `prom-client`).

| Metric | Type | Labels |
| ------ | ---- | ------ |
| `http_requests_total` | counter | `method`, `route`, `status_code` |
| `http_request_duration_seconds` | histogram | `method`, `route`, `status_code` |
| `http_requests_in_flight` | gauge | — |
| `db_query_duration_seconds` | histogram | `operation`, `result` |
| `db_pool_connections` | gauge | `state` |
| `process_*`, `nodejs_*` | various | — (CPU, RSS, heap, event loop lag, GC) |

Three things worth knowing, all of which matter under load:

- **The `route` label is the route *pattern*** (`/api/users/:id`), never the raw
  URL. Labelling by URL would mint a new time series per user id and per email
  address — the standard way to blow up Prometheus cardinality. Requests that
  matched no controller collapse into a single `route="unmatched"` series. See
  [`route-pattern.ts`](src/common/route-pattern.ts).
- **Aborted requests are counted.** The middleware settles on `close` as well as
  `finish`, so client timeouts — routine during a load test — still record their
  metric and access log. Listening only to `finish` would let
  `http_requests_in_flight` ratchet upward forever.
- **`db_pool_connections{state="pending_acquires"}` is the number to watch.** A
  non-zero value means requests are queueing for a database connection, i.e. the
  pool (`DB_POOL_MAX`), not Postgres, is the bottleneck.

`/metrics` is excluded from both the access log and HTTP metrics (`/docs` and
its assets never reach the middleware at all) — see
[`observability-exclusions.ts`](src/common/observability-exclusions.ts) for why
that is not done with Nest's `MiddlewareConsumer.exclude()`.

Minimal scrape config:

```yaml
scrape_configs:
  - job_name: backend
    static_configs:
      - targets: ['localhost:3000']
```

## Row hydration (knexnest)

Query results are hydrated by [knexnest](https://www.npmjs.com/package/knexnest),
which builds the response objects from the **column aliases** rather than from a
hand-written mapping function. See `USER_COLUMNS` in
[`users.repository.ts`](src/users/users.repository.ts).

Two rules govern the aliases:

- A leading `_` marks the root of the structure and makes the result a list.
- `_` is also the **nesting delimiter**, so aliases must be camelCase.
  `first_name as _first_name` hydrates as `{ first: { name } }`, not `firstName`.
  knexnest does not case-convert — the camelCase is declared by the alias.

Nested shapes use `__`, e.g. adding
`'p.title as _posts__title'` to a joined query nests a `posts` array under each
user with no extra mapping code. That is the reason to use it here.

Two behaviours worth knowing:

- An empty result set resolves to **`null`**, not `[]`, unless the second
  argument `listOnEmpty` is `true`. Every call site passes `true`.
- Aggregates (`count()`) have no structure to hydrate and stay on plain Knex.

knexnest ships no types; the local declaration is in
[`src/types/knexnest.d.ts`](src/types/knexnest.d.ts).

## Notes

- `id` is a `bigint`, which exceeds `Number.MAX_SAFE_INTEGER`, so it is returned
  as a **string** in JSON and handled as a string throughout the code.
- `created_at` is `timestamptz`; Postgres normalises it to UTC on write. It is
  hydrated as a `Date` and serialised as an ISO-8601 `Z` string by `Date#toJSON`.
